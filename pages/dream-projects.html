#1 — Modular Cyberdeck In Progress

Hardware · Raspberry Pi 5 · Python · Shell · CircuitPython

A fully custom, hand-built portable computer — not a laptop, not a tablet, something entirely mine. Based on the open-source DFCD (DesignatedFreeCadDevice): Raspberry Pi 5 8GB brain, sliding 10.1" touchscreen, hidden NOS C-450 TKL mechanical keyboard, Logitech Marble trackball, NP-F battery, and a rotary encoder scroll handle. Every part is either 3D-printed or off-the-shelf — nothing is welded or machined. The point is a machine shaped around how I actually work — the keyboard I want, one-handed trackball navigation, and a rotary encoder for scrolling long documents and code.

What's already built (software side):


✓ Full custom OS layer for Raspberry Pi OS — idempotent installer, systemd boot scripts, zram memory tuning, themed terminal
✓ Opt-in AI layer — Claude Code + Ollama, memory-tuned for Pi 5
✓ Opt-in extras — deck-mode (stealth/work/bright), deck-vault (LUKS2 encrypted container), Conky status bar, RTL-SDR radio
✓ Grimoire — offline documentation search engine (SQLite + BM25 FTS5, ingest from DevDocs .zim files)
✓ Clamp-on Comms module — Pico USB bridge, NFC (PN532) + LoRa (RFM9x, 923 MHz AS923), custom CAD enclosure, CircuitPython firmware
✓ Custom 3D-printed parts — raised GFPIO lid, modified screen frame with status LED
✓ Full build guide (PDF), bill of materials, shopping lists (USD + THB)


What's blocking the physical build:


Cost of the mechanical keyboard components and the 3D printing time for the chassis parts. I've been planning this since June 2026, and the software side is done — the OS and app layers install cleanly today. What's left is the enclosure and buying the parts, so it's purely a cost and time problem at this point.

#2 — Petri In Progress

Rust · egui · Linux

This one started with Rubber Ducky USB attacks — I wanted somewhere to run something sketchy without handing it my actual laptop. What it turned into is a desktop app for running benign, simulated malware specimens: small programs I write myself that mimic a malware behaviour, so I can take them apart and watch what they do without any of it being real. You create a named sandbox, hand it an explicit set of permissions, drop a specimen in, and read the log.


What's built so far:


✓ Sandbox lifecycle as a real state machine — Created → Starting → Running → Stopping → Stopped → Destroyed, with illegal transitions refused instead of tolerated
✓ Opt-in permissions — ReadFiles, WriteFiles, ExecutePrograms, NetworkAccess; a new sandbox starts with none of them
✓ Isolation tracked as its own axis, separate from run state, so a sandbox can only be isolated from Running or Stopped
✓ Per-sandbox storage — everything lives under sandboxes/sandbox-<id>/ with files/ and logs/, thrown away afterwards
✓ egui desktop shell, written from scratch with no framework underneath it


What isn't built yet — being straight about it:


The containment is designed, not implemented. isolate_sandbox() flips an enum and returns Ok — there is no namespace, jail, seccomp or container behind it yet, there are no specimens to detonate, and the crate does not compile clean right now. Nothing in it is safe to point at anything real. What's blocking it is time, and learning Rust at the rate the problem actually needs — I'd rather say that than ship something that only looks like a sandbox.
